# Standard matcher baseline: macOS ARM64, 2026-10-23

The extension is faster on the larger bundled Australian reference and survives a
10,000-input batch under a memory cap that stops the Python implementation. It is
not yet behaviorally interchangeable with Python: reference tokenization, Unicode
normalization, and tie ordering change results. Controlled diagnostics reproduce
Python's labels and scores exactly on both fixture sets when those choices align.

## Reproduction

Measured clean revision: `a39327811d0589aa0e97725b6d5943918bfcaff4`, based on extension
revision `4e0891e5b3d04803154e9df6954bb031d65600af`. Native extension, macOS 26.5.2 ARM64,
Python 3.12.15, DuckDB 1.4.2, one DuckDB thread, `memory_limit=1GB`, seed 20261023.
The machine reports eight logical CPUs. Three measured repetitions follow a first
call and one excluded warmup, in separate sequential worker processes.

```sh
uv run python extensions/duckdb/benchmarks/compare.py \
  --dataset all --samples 128 --sizes 100 1000 10000 \
  --repeats 3 --warmups 1 --threads 1 --memory-limit 1GB \
  --extension extensions/duckdb/build/whereabouts.duckdb_extension \
  --out extensions/duckdb/build/baseline-macos-arm64-v2
```

See the [methodology](../README.md) for prerequisites and measurement boundaries.
[Raw summary](macos-arm64-2026-10-23.json) includes timings, accuracy by category and
threshold, hashes, and both worker failures. The overall run exited with status 2
because of the two reported out-of-memory failures; the remaining jobs completed.

## Speed and memory

Warm median elapsed seconds, including fetching the same five output columns for
both query paths. API timings additionally include conversion and a richer payload.
The Australian reference contains 18,687 records; Poland contains only 121.

| Reference | Input rows | Python query | Extension query | Query speedup | Python API |
|---|---:|---:|---:|---:|---:|
| Australia | 100 | 0.332 | 0.086 | 3.88x | 0.343 |
| Australia | 1,000 | 3.230 | 0.736 | 4.39x | 3.192 |
| Australia | 10,000 | Out of memory | 7.352 | Not measurable | Out of memory |
| Poland | 100 | 0.0061 | 0.0074 | 0.82x | 0.0112 |
| Poland | 1,000 | 0.0191 | 0.0131 | 1.46x | 0.0384 |
| Poland | 10,000 | 0.1450 | 0.0685 | 2.12x | 0.2981 |

The extension is slightly slower for the smallest Polish query. Millisecond-scale
differences on this tiny reference need repeated full runs before generalization.
Python API overhead is small relative to matching on the Australian reference.

Australian 1,000-row worker peak RSS was 266 MiB for the extension and 410 MiB for
the Python query. The 10,000-row extension worker reached 1,081 MiB and processed
about 1,360 rows/sec. RSS includes the Python host, libraries, inputs, and results;
the 1 GB DuckDB memory limit is not a total process limit. These failures do not
show that Python cannot process 10,000 inputs with more memory or smaller batches.

Build observations were 0.149 s extension versus 0.307 s Python for Australia,
and 0.008 s versus 0.082 s for Poland. These are single observations, exclude source
file reading/loading, and do not establish country-scale build performance.

## Accuracy and compatibility

These are synthetic regression cases derived from the reference, including exact
inputs and edits. Positive recall below means correct label / all positive cases
at threshold 0; precision means correct / returned. Neither is a production accuracy
estimate. Negative cases are deliberately easy: 20 disjoint addresses plus three
empty/NULL inputs per dataset. Both implementations rejected all 23 in each dataset.

| Generated cases | Python correct / positive | Extension correct / positive | Python precision | Extension precision |
|---|---:|---:|---:|---:|
| Australia | 586 / 634 (92.43%) | 592 / 634 (93.38%) | 92.87% | 93.82% |
| Poland | 253 / 405 (62.47%) | 381 / 405 (94.07%) | 99.22% | 96.46% |

Polish recall improves alongside more wrong accepted matches: 14 versus Python's
two. At threshold 0.5, Polish Python recall falls to 51.85% with 99.06% precision;
extension recall/precision are unchanged. Score thresholds therefore do not have
equivalent meaning across these implementations. All thresholds in the summary
are applied in identical postprocessing, since the Python standard path does not
apply its exposed threshold setting.

Exact generated labels were correct for 127/128 Australian extension cases versus
126/128 Python cases, and 121/121 Polish extension cases versus 93/121 Python cases.
Typos remain a weakness: Australia 90/128 versus 88/128, Poland 97/121 versus 47/121.
Some edits introduce ambiguity, so these differences need human adjudication.

Only **one of the 244 independently supplied Australian expected labels** exists
in the bundled reference. Both implementations found that one. At threshold 0 they
also returned 53 wrong matches among the other 243 cases; threshold 0.5 rejected
all those wrong matches. This dataset cannot establish general held-out accuracy
without its corresponding reference corpus. The benchmark never adds answers to
the reference database.

Top-label agreement with Python across all cases is 90.68% in Australia (901 cases)
and 66.82% in Poland (428 cases). Identical labels include identical no-match results.
Agreement is distinct from correctness. The largest distance between predictions
was about 2.40 km and 4.63 km respectively; these are disagreements, not measured
errors against independently surveyed coordinates.

## What explains the differences?

The [diagnostic results](macos-arm64-2026-10-23-diagnostics.json) come from untimed,
in-memory SQL overrides after the benchmark. They do not change extension source,
the native binary, or the measured baseline.

1. **Tie order:** Python sorts reference IDs numerically; the extension's generic
   string IDs sort lexically. On the shared Python reference/index, changing the
   extension's `ORDER BY similarity DESC, reference_id` to
   `ORDER BY similarity DESC, TRY_CAST(reference_id AS BIGINT)` removes all 78
   Australian label/score disagreements. All 901 results then match Python.
   Arbitrary nonnumeric IDs need a deliberate policy before adopting such a change.
2. **Numeric reference tokens:** 372 of 18,687 Australian reference records have
   different numeric-token lists. Python retains a whole token containing digits
   (for example `D311`); the extension extracts `311`. The shared-reference control
   removes this difference. Unit/lot identifiers need explicit compatibility tests.
3. **Unicode input/reference normalization:** Python's reference builder preserves
   Unicode, but its standard input pipeline uses `unaccent` and ASCII token rules.
   For example `Bolesławiec` becomes `BOLESLAWIEC` on that input path, while the
   extension's `strip_accents` preserves `Ł`. On the shared reference with numeric
   ties, applying Python's input normalizer and ASCII token extraction removes all
   remaining Polish disagreements; all 428 labels and scores then match Python.

To reproduce the last diagnostic, attach the run's `reference.duckdb`, register its
`cases.json` as `input_addresses(address_id, address)`, load the SQL macros with the
numeric ordering replacement above, and override these input helpers:

```sql
CREATE OR REPLACE MACRO wa_normalize(address) AS
  trim(regexp_replace(regexp_replace(unaccent(upper(address)),
    '[^A-Z0-9]+', ' ', 'g'), '[ ]+', ' '));
CREATE OR REPLACE MACRO _wa_alpha(address) AS
  regexp_extract_all(address, '[A-Z]+');
CREATE OR REPLACE MACRO _wa_numerics(address) AS
  regexp_extract_all(address, '[0-9]+[A-Z]?');
-- LOAD splink_udfs supplies unaccent. Compare to the saved Python predictions.
SELECT * FROM wa_geocode('input_addresses', 'remote.shared_reference', 'remote.shared_index');
```

## Before upstream release

- Decide whether to promise Python compatibility or document improved generic
  normalization, and add regression fixtures for unit identifiers, Unicode and ties.
- Obtain representative held-out labels with adequate reference coverage and
  realistic ambiguous/no-match inputs; adjudicate discrepancies and calibrate cutoffs.
- Measure larger references, multiple thread counts and memory caps, and repeat
  trials on Linux and macOS. The manual CI workflow is supplied but was not run here.
- Measure country-scale index/storage costs and establish regression tolerances.
  Trigram and reverse-geocoding remain outside this standard-matcher extension.
